Cómo comprobar la mejora

  1. Guarda una línea base con la carga real representativa y al menos tres repeticiones.
  2. Cambia un factor. Reinicia si corresponde y conserva versiones, datos y condiciones térmicas.
  3. Repite la batería, compara medianas, dispersión, p95 y consumo medido. Comprueba errores y estabilidad.
  4. Acepta la mejora solo si cumple el objetivo sin empeorar las restricciones acordadas. Documenta cómo revertirla.
Ley de Amdahl: si solo mejoras un factor de la CPU, la aceleración del tiempo total sería 1 / [(1 − f) + f / s]. Con f = 0.40 y s = 2, resulta 1.25×. Este ejemplo explica el límite; el simulador utiliza el modelo de capacidades descrito en «Modelo y fuentes».
04 / BATERÍA DE PRUEBAS

Del modelo al equipo real

Software, cargas sintéticas y pruebas representativas para repetir el estudio fuera de esta app.

Procedimiento común de medición

  1. Preparar: inventario, copia de seguridad, corriente estable, espacio libre, versiones y ambiente. Usa datos de prueba y una ventana autorizada.
  2. Instrumentar: registra cada segundo CPU total y por núcleo, RAM disponible, paginación, latencia de disco, tráfico de red, reloj efectivo, temperatura y errores. En Windows: Monitor de rendimiento; en Linux: herramientas del sistema y registros.
  3. Separar fases: reposo 2 min, calentamiento 2–5 min, medición estable 5–15 min y enfriamiento. Son duraciones iniciales didácticas; amplíalas hasta observar estabilidad térmica o cubrir el ciclo real.
  4. Repetir: al menos 3 ejecuciones independientes por configuración, alternando el orden A/B para reducir sesgos. Si hay mucha dispersión, investiga y amplía las repeticiones.
  5. Conservar: archivos de entrada, versiones, configuración de prueba, registros originales, semilla si aplica y criterio de aprobación fijado antes de medir.
  6. Detener: si aparecen errores, corrupción, reinicios o límites térmicos del fabricante. Una prueba breve sin errores no certifica estabilidad prolongada.

06 / TRANSPARENCIA DEL MODELO

Qué significan los números

Supuestos explícitos para interpretar la simulación y trasladar el aprendizaje a una evaluación real.

Modelo educativo de capacidades

Cada perfil tiene una capacidad hipotética de CPU, disco, GPU y red expresada en unidades equivalentes de trabajo por segundo. La RAM se modela en GB. Estas unidades internas permiten comparar dentro del escenario y no equivalen a puntuaciones de OCCT, Blender o sysbench.

λ = demanda de referencia × carga × patrón × variación RAM útil = 0.8 × RAM instalada P = max(0, datos activos / RAM útil − 1) CPU efectiva = CPU × (1 − overhead) × factor térmico Disco efectivo = disco / (1 + 2 × P) Capacidad C = min(capacidad efectiva / demanda por unidad) Throughput X = min(λ, 0.98 × C) ρ = λ / C Rmedio = 1000 / max(C − λ, 0.02 × C) p95 ilustrativo = −ln(0.05) × Rmedio Pendientes = max(0, pendientes + (λ − X) × Δt)

La aproximación de respuesta se inspira en una cola M/M/1 equivalente. Cerca de saturación limita la espera para mantener la gráfica legible; cuando λ ≥ C la cola no tiene régimen estable. En esa región, el p95 es solo un indicador acotado y no predice la latencia real. Los pendientes muestran la acumulación.

La gráfica utiliza 31 muestras y una variación pseudoaleatoria de ±4%. Cada muestra representa un intervalo de duración/30 segundos. Las tres réplicas emplean semillas consecutivas. El throughput mostrado es la media temporal; el p95 mostrado es la media de estimadores por intervalo, no un percentil empírico de peticiones.

Tiempo de tarea y controles sencillos

Ligero, habitual e intenso ajustan la cantidad al 50%, 100% y 160% de la referencia de cada prueba. Cada cambio ajusta la memoria de trabajo a RAM de referencia × (0.5 + 0.5 × carga/100), redondeada a 2 GB. Puedes modificarla después en los ajustes avanzados. Cantidad no significa concurrencia real salvo cuando la etiqueta lo indica.

Tiempo de tarea = cantidad redondeada × costo abstracto por elemento / throughput medio. El costo por elemento está definido en el catálogo de tareas del código; no procede de mediciones. Para servicios interactivos se muestra un diagnóstico de espera en lugar de un tiempo de lote. Los modelos ZIP/RAR no predicen el tamaño final: hay que medirlo con los mismos archivos reales.

Temperatura, demanda y límites

Temperatura estimada = ambiente + 12 + 48 × uso CPU (máximo 1) × (1 − exp(−tiempo/90)) + 8 × P. La mejora de refrigeración resta 12 °C. Por encima de 85 °C, el modelo reduce la capacidad CPU 1.5% por grado, hasta un mínimo de 55%. Este umbral es didáctico: consulta el límite del componente real.

Las presiones de CPU/disco/GPU/red se calculan con la demanda ofrecida, no solo con el trabajo completado. Las barras pueden superar 100%; la ocupación de la gráfica se limita a 100%. RAM indica ocupación respecto a RAM útil y puede provocar penalización por paginación.

El costo de tuning es una suma de importes ficticios en unidades monetarias (u.m.). La potencia es una estimación lineal a partir del uso y las mejoras; no proviene de sensores. No se modelan cachés reales, NUMA, VRAM, redes externas, compatibilidad, instrucciones de CPU ni fallos de hardware. Cada prueba de software cambia la mezcla de demanda de CPU, disco, GPU y red, y la memoria de referencia. Es una aproximación conceptual, no la ejecución de ese programa.

No confundir: una animación de carga no es un estrés real del dispositivo. No uses estas cifras para certificar un equipo, comprar una marca o establecer límites térmicos.

Aclaraciones didácticas

El throughput y el tiempo de respuesta no son inversos universales. La ley de Little, N = X × R, relaciona población media, throughput y respuesta en un sistema estable con límites coherentes. La utilización óptima depende del servicio; no existe un porcentaje ideal universal.

Conceptos para interpretar

HB · Mayor es mejor
Throughput, trabajos por segundo o ancho de banda, manteniendo calidad y errores controlados.
LB · Menor es mejor
Latencia, tiempo de ejecución, errores o energía por trabajo.
NB · Nominal es mejor
Un intervalo objetivo, como una ocupación que conserve margen ante picos. Una CPU al 100% puede ser normal en render, pero indeseable en un servicio sensible a latencia.
p95 y mediana
El p95 real es el valor por debajo del cual cae el 95% de las observaciones. La mediana es el centro ordenado. Conserva observaciones originales para calcularlos.
Variabilidad y CV
CV = desviación estándar muestral / media × 100. Con tres réplicas solo hay una primera señal de dispersión, no una certificación estadística.
Monitor
Sensor → transformación → indicador. Observar también consume recursos: registra el overhead de la instrumentación.
